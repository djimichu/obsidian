# Каналы.
## Не буферизированные. 

#### 🔹 **Главная идея: синхронизация через блокировку**

Unbuffered канал работает как "точка встречи" двух горутин.

### ✔ Как работает отправка (`send`)

```go
ch <- x
```

Send блокируется **до тех пор**, пока другая горутина **не сделает receive**.

Почему?  
Потому что в небуферизированном канале **нет места, куда положить значение**.  
Единственный способ доставить данные → сразу передать в руки принимающей горутины.

### ✔ Как работает чтение (`receive`)

x := <-ch

Receive блокируется **пока нет send’a**.

Почему?  
Потому что нечего читать — буфера нет.

---

### 🔹 **Ключевой механизм: передача происходит напрямую**

Передача значения из одной горутины в другую происходит **без промежуточного хранения**.

То есть:

```
sender ---- x ----> receiver   (в реальном времени)
```

Нет очереди, нет буфера. Имитация "встречи":

- обе стороны должны прийти к операции
    
- runtime соединяет их
    
- передаёт значение
    
- обе горутины продолжают выполнение

### 🔹DEADLOCK 

Если никто не читает из канала происходит вечная блокировка
## Буферизированные.

### 🔹 **Главная идея: есть промежуточное хранилище**

Buffered канал содержит FIFO очередь фиксированного размера.

Например:
```
ch := make(chan int, 3)
```

### ✔ Как работает отправка (`send`)

- Если в буфере **есть место** → send _не блокируется_
    
- Если буфер **полон** → send _блокируется_, пока кто-нибудь не сделает recv

#### Поведение:

```
⭕ первый send → кладёт в буфер
⭕ второй send → кладёт в буфер
⭕ третий send → кладёт в буфер
❌ четвёртый send → блокируется
```

---

### ✔ Как работает чтение (`receive`)

- Если в буфере **есть данные** → recv _не блокируется_
    
- Если буфер **пуст** → recv _блокируется_, пока кто-то не сделает send

---

### 🔹 Почему buffered канал быстрее?

Потому что goroutine отправитель **не ждёт** моментального сопряжения с получателем.  
Меньше контекстных переключений, меньше блокировок → выше пропускная способность.

---

### 🔹 Почему слишком большой буфер — плохо?

Хотя буфер снижает блокировки, он:

- увеличивает задержку (данные могут долго лежать в очереди)
    
- увеличивает потребление памяти
    
- может скрывать проблемы синхронизации
    
- может привести к burst-эффекту (накопилось → отработало рывком)

На собесе любят спросить:

> "Почему не стоит ставить буфер размером 10000?"

Ответ: буфер — это очередь, а большие очереди = большие задержки.

## Worker Pool.

### 🧱 Что такое Worker Pool
**Worker Pool (пул воркеров)** — это **паттерн параллельного выполнения**, в котором:

1. Есть **задачи** (jobs)
    
2. Есть фиксированное количество **воркеров** (рабочих горутин)
    
3. Есть **канал**, через который воркеры получают задачи
    
4. Все воркеры работают параллельно, пока задачи не закончатся

Паттерн нужен, когда задач много, а количество системных ресурсов ограничено.

### 🚀 Зачем нужен worker pool?

Он решает три ключевые проблемы:

 1) **Ограничение параллелизма**

Если у тебя 100k задач, нельзя запускать 100k горутин — память взорвётся.

Пул запускает, например, **10 воркеров**, и они обрабатывают задачи порциями.

---

2) **Устранение чрезмерного контекста переключения**

Много горутин → много переключений → хуже производительность.

Пул держит фиксированное число горутин.

---

 3) **Балансировка нагрузки**

Все воркеры получают задачи из общего канала → равномерная обработка.

### ⚠️ Важный момент

Worker pool **всегда подразумевает закрытие входного канала** (jobs).

Почему? Иначе воркеры никогда не выйдут из цикла и программа зависнет → deadlock.

> [!example]- 🛠 Простой пример Worker Pool
> 
> Допустим, есть 5 воркеров и 20 задач.
> 
> ```go
> package main
> 
> import (
>     "fmt"
>     "time"
> )
> 
> func worker(id int, jobs <-chan int, results chan<- int) {
>     for job := range jobs {
>         fmt.Printf("worker %d started job %d\n", id, job)
>         time.Sleep(200 * time.Millisecond) // имитация работы
>         fmt.Printf("worker %d finished job %d\n", id, job)
>         results <- job * 2
>     }
> }
> 
> func main() {
>     jobs := make(chan int, 20)
>     results := make(chan int, 20)
> 
>     // запускаем 5 воркеров
>     for w := 1; w <= 5; w++ {
>         go worker(w, jobs, results)
>     }
> 
>     // отправляем 20 задач
>     for j := 1; j <= 20; j++ {
>         jobs <- j
>     }
>     close(jobs) // ВСЕГДА закрываем jobs
> 
>     // собираем результаты
>     for r := 1; r <= 20; r++ {
>         <-results
>     }
> }
> ```

> [!success]- 🔍 Пошагово — что здесь происходит
> 
> #### 1) Создаём 2 канала
> 
> - `jobs` — куда кладём задачи
>     
> - `results` — куда воркеры кладут результаты
>     
> 
> #### 2) Запускаем 5 воркеров
> 
> Каждый воркер:
> 
> - блокируется на чтении `jobs`
>     
> - как только получает задачу → обрабатывает
>     
> 
> #### 3) Кладём задачи в канал `jobs`
> 
> #### 4) Закрываем `jobs`
> 
> После закрытия:
> 
> - воркер, который пытается прочитать, получает `job == zero value`, но `ok == false`
>     
> - выходит из цикла `for job := range jobs`
>     
> 
> #### 5) Собираем результаты
