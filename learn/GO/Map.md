[[Хэш-таблица]] - основной материал по мапам


## 1. Внутреннее устройство `map`

Go-map — это **хеш-таблица с гибридной адресацией**, но в стиле Go:

### ✔ Основные элементы:

- **hmap** — заголовок карты (len, count, pointers).
    
- **buckets** — массив бакетов; размер всегда 2^B.
    
- **bucket**:
    
    - 8 слотов под ключи/значения.
        
    - `tophash[8]` — первые 8 бит хеша для быстрого отсечения.
        
    - Если коллизий больше — **overflow bucket** (сингл-линк список).
        

### ✔ Хеширование

- Используется алгоритм, зависящий от рантайма (SipHash-бейз).
    
- Хеш состоит из:
    
    - _tophash_ (8 бит) — быстрый фильтр.
        
    - Полный хеш — используется для выбора bucket: `bucket = hash & (2^B - 1)`.
        

### ✔ Порядок обхода

- Go **рандомизирует порядок итерации**, т. к. каждый запуск получает случайную seed.
    
- Это делается для защиты от атак и отсутствия гарантии стабильности.
    

### ✔ Пример визуализации bucket:

```
bucket:
    tophash: [0x12, 0x54, 0x00, 0xAA, 0x11, 0x22, 0x33, 0x44]
    keys:    [k1, k2, nil, k3, k4, k5, k6, k7]
    values:  [v1, v2, nil, v3, v4, v5, v6, v7]
    bucket -> overflow -> overflow
```

Коллизии сваливаются в overflow-цепочки.


## Почему `map` **не потокобезопасна**

Go **не допускает конкурентную запись** (read+write или write+write), потому что:

1. **Resize происходит lazily**, во время обычных операций — запись в map может:
    - переместить бакеты,
        
    - изменить указатели,
        
    - изменить порядок элементов.
        
2. Итерация и запись тоже конфликтуют:
    
    - итератор может обходить старые/новые бакеты при resize,
        
    - в этот момент структура может измениться → race.
        
3. Go не использует lock внутри `map`:
    
    - чтобы не ухудшать производительность,
        
    - потому что пользователь всегда может обернуть map в мьютекс.

Для этого есть `sync.Map` и `sync.RWMutex + map`.

- Когда load factor превышает ~6.5 элементов на бакет → **grow(resize)**
    
- B увеличивается на 1 → количество бакетов удваивается:

## sync.Map
#### Как устроен `sync.Map` внутри

Упрощённо: там **два слоя**:

- **read-only map** (только для чтения) — быстрый путь для `Load` без блокировок
    
- **dirty map** (грязная) — туда идут новые записи/изменения; защищена мьютексом
    

И есть механизм “промоушена”:

- если много промахов (`Load` не нашёл в read-only и полез в dirty),
    
- runtime “повышает” dirty → read-only, чтобы чтения снова стали быстрыми.
    

Собеседовательная формулировка:

> `sync.Map` оптимизирован под чтение: сначала смотрит в read-only без lock; при промахе берёт lock и смотрит dirty; при накоплении промахов dirty периодически промоутится в read-only.

Этого достаточно. В детали счетчиков/entry можно не уходить, если не просят.


## Новая мапа

В новой мапе вместо бакетов используются группы в массиве, они также номеруются и с помощью младших битов(010) выбирается номер группы, групп всегда 2^B(сперва 2, потом +1), число младших битов = B.

У каждой группы есть 64-битное (8-байтовое) контрольное слово: по 1 байту метаданных на слот. 1 бит показывает заполненность, а 7 бит (H2) показывают младшие биты хеша.
Также есть 57 бит, H1, которые показывают старшие биты.
