# Ответ
Если спросят “как реализован mutex в Go”:

Можно сказать так:

> В Go mutex реализован через **атомарные операции** Compare-And-Swap(CAS) для быстрого захвата, а при контеншене горутины паркуются через runtime-семафоры. Он также обеспечивает happens-before гарантии по memory model.

--- 
```go
type Mutex struct {  
    state int32  // битовое поле состояния
    sema  uint32  // семафор рантайма для блокировки/разблокировки горутин
}
```
`state` кодирует несколько вещей:

```
locked      = 1 << 0  :мьютекс занят
woken       = 1 << 1  :одна горутина уже разбужена
starving    = 1 << 2  :режим starvation
waiterShift = 3       :количество ожидающих
```
## Устройство
##### 🔹 *Шаг 1 — попытка захвата*

Когда вызывается:

```go
mu.Lock()
```

происходит примерно следующее:

1. Пытаемся **атомарно** изменить `state` с 0 на 1.  
    Это делается через CAS (Compare And Swap — “сравнить и заменить”).
    

CAS — это операция процессора, которая:

- проверяет: равно ли значение X?
    
- если да → меняет его
    
- и делает это неделимо (за один шаг)

Если CAS прошёл успешно → ты захватил мьютекс.

##### *🔹 Шаг 2 — если уже занят*

Если `state` уже равен 1:

- горутина сначала немного “покрутится” (короткое ожидание)
    
- если не освободился → её **усыпляют**
    
- она снимается с процессора
    
- помещается в очередь ожидания
    

То есть она не грузит CPU.


##### 🔹 *Шаг 3 — освобождение*

Когда вызывается:

mu.Unlock()

происходит:

1. `state` меняется обратно
    
2. если есть ожидающие — одного из них **будят**
    

Разбудили → он снова пытается захватить через CAS.

## Важный момент — гарантия памяти

Мьютекс не просто “закрывает участок кода”.

Он гарантирует:

> Всё, что записано до `Unlock()`, станет видно тому, кто после этого выполнит `Lock()`.

Это правило порядка операций в памяти.

Именно поэтому mutex защищает данные корректно.

## Почему нельзя копировать Mutex

Поведение программы становится непредсказуемым.

Если ты скопируешь структуру, внутри которой есть `Mutex`, то:

- скопируется состояние блокировки
    
- но очередь ожидающих — нет
    
- внутри будет сломанное состояние
    

И программа может:

- зависнуть
    
- паниковать
    
- вести себя странно
    

Поэтому правило:

> Mutex нельзя копировать после начала использования.

## RWMutex и Mutex

> Чем `Mutex.Lock()` отличается от `RWMutex.Lock()`?

Правильный ответ:

- `Mutex.Lock()` просто ждёт освобождения.
    
- `RWMutex.Lock()` дополнительно ждёт завершения всех текущих читателей и блокирует вход новых читателей.

Отличие Lock от RLock
- RLock → “много читающих, никто не пишет” : Пока есть хоть одна горутина с RLock - никто не пишет.
    
- Lock → “один внутри, остальные ждут” : Когда какая-то горутина вызвала Lock - новые читатели уже не пускаются. Будут ждать пока писатель отработает.
