# Введение.

##### Индекс - это структура данных, ускоряющая выборку данных из таблицы за счёт доп. операций записи и использования доп. пространства на диске, используемых для хранения структуры данных и поддерживания её в актуальном состоянии.


> [!tip]- Для понимания сути
> id | name     | email               | age
---|----------|---------------------|----
1  | Иван     | ivan@mail\.com       | 25
2  | Анна     | anna@mail\.com       | 30  
3  | Петр     | petr@mail\.com       | 35
4  | Мария    | maria@mail\.com      | 28
1,000,000 | ... | ... | ...
> Запрос без индекса:
> > [!example]-
> > ```sql
> > SELECT * FROM users WHERE email = 'ivan@mail.com';
> > -- PostgreSQL: "Окей, проверю ВСЕ 1 млн записей одну за другой"
> > -- Время: 1 секунда
> > ```
> 
> Запрос с индексом:
> > [!example]-
> > ```sql
> > -- Тот же запрос, но есть индекс на email
> > SELECT * FROM users WHERE email = 'ivan@mail.com';
> > -- PostgreSQL: 
> > -- 1. "Открою индекс (оглавление) emails"
> > -- 2. "Быстро найду 'ivan@mail.com' (бинарный поиск!)"  
> > -- 3. "Ага, это строка #1"
> > -- 4. "Возьму только строку #1 из таблицы"
> > -- Время: 0.001 секунды (в 1000 раз быстрее!)
> > ```
> >

### Устройство БД.

- database cluster - одна и более БД, управляемые из под одной инстанции сервера
- Файлы данных кластера лежат в директории data (часто называемой PGDATA)
- Для каждой БД есть своя подпапка в PGDATA/base
- Для каждой таблицы и индекса выделяется отдельный файл (обычно 1 ГБ)
- Таблица состоит из массива страниц (блоков, размером 8кб по умолчанию)
- Файл таблицы называется **Heap File** - содержат списки неупорядоченных записей различной длины

---

- Рядом с файлом таблицы лежит файл FSM(free space map)
	- Он хранит значение округленные до 1/256 от размера страницы - это 32 байта при размере таблицы в 8 Кб. Используется для того, чтобы сервер понимал, куда можно сохранить данные определенных размеров.
	- FSM не обновляется при каждом удалении или обновлении строк. Это нужно для того, чтобы поддерживать механизм конкурентного доступа(параллельного) к одним и тем же данным.
- VACUUM \[FULL] - команда для очистки "дохлых" версий строк
	- Она не возвращает ОС память, а просто помечает определенные отрезки памяти для сервера как такие, которые можно спокойно перезаписывать новыми данными. Т.е. ничего не удаляет, а просто помечает для последующей перезаписи.
	- \[FULL] производит сжатие таблицы и полную ее перезапись, проводя дефрагментацию данных. Операция требует столько же памяти, сколько занимает таблица, на которую натравили  VACUUM \[FULL]. Делается редко.
- Рядом с файлом таблицы лежит файл VM (visibility map)
	- Хранит биты, 1бит на страницу, которые будучи единицей, показывает, что страница не содержит протухших версий строк. Это оптимизационный механизм, позволяющий серверу быстрее считывать данные.

### VACUUM

В устройстве БД мы кратко прошлись по VACUUM, тут чуть подробнее.

- Если вообще не обслуживать БД, то фрагментация данных будет нарастать
- VACUUM - команда для очистки "дохлых" версий строк
- VACUUM FULL  - полный "компактинг" таблицы
- Необходим периодический запуск VACUUM
- Активно обновляемым БД рекомендуется проходить VACUUM каждую ночь
- VACUUM FULL только если удалили много данных
- VACUUM ANALYZE - комбинация двух операций
	- ANALYZE собирает статистику о содержимом в таблицах и сохраняет результаты в специальном системном каталоге pg_statistic и как результат, планировщик запросов после этого может использовать статистику для того чтобы определить наиболее эффективный план выполнения запросов. Если никаких параметров команде ANALYZE не дано, то ANALYZE пройдет по всем таблицам в текущей БД. А с параметрами можно указать на конкретные таблицы.
- Autovacuum демон(бэкграунд процесс) делает всё автоматически
	- Его работа базируется на собираемой сервером статистике апдейтов и удалений. Включается этот демон эврестически(алгоритм рабочий, но не идеальный).
	- Содержит кучу настраиваемых параметров 
	- По умолчанию механизм Autovacuum включён, отключать его не рекомендуется
