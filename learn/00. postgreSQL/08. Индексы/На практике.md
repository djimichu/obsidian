# Простые индексы на деле.

### Подготовка таблицы для примеров
```sql
-- 1. Создаём таблицу для тестов производительности
CREATE TABLE perf_test(
    id int,                     -- просто номер
    reason text COLLATE "C",    -- случайный md5, сравниваем быстро
    annotation text COLLATE "C" -- будет заполнено позже
);

-- 2. Вставляем 10 миллионов записей
INSERT INTO perf_test(id, reason, annotation)
SELECT 
    s.id,                     -- 1, 2, 3, ..., 10,000,000
    md5(random()::text),      -- случайный хэш типа 'd3d9446802a...'
    null                      -- пока пусто
FROM generate_series(1, 10000000) AS s(id)  -- генератор 1-10M
ORDER BY random();  -- перемешать! (чтобы не было кластеризации - для тестов лучше чтобы значения шли в рандомном порядке, так будет наглядно понятно)

-- 3. Обновляем annotation тоже случайными строками
UPDATE perf_test
SET annotation = UPPER(md5(random()::text));
-- UPPER делает все буквы заглавными: 'abc' → 'ABC'
```

> [!tip]- md5(random()::text) пояснение
> ```sql
> -- Изнутри наружу:
> 1. random() → случайное число 0.0-1.0 (например 0.735829)
> 2. random()::text → превращает в текст '0.735829'
> 3. md5('0.735829') → хэширует в 32-символьную строку
> -- Результат: 'd3d9446802a44259755d38e6d163e820'
> ```

> [!tip]- COLLATE пояснение
> ### Без `"C"` (обычный текст):
> 
> ```sql
> reason text  -- PostgreSQL: "Ок, сравнивай с учётом локали"
> -- Сравнение: 'apple' = 'Apple'? (зависит от настроек)
> -- Сортировка: 'ё' отдельно или после 'е'? (зависит)
> ```
> ### С `"C"` (байтовое сравнение):
> 
> ```sql
> reason text COLLATE "C"  -- PostgreSQL: "Сравнивай ASCII коды!"
> -- 'A' = 65, 'B' = 66, 'a' = 97, 'b' = 98
> -- 'apple' < 'Apple' (потому что 'a'(97) > 'A'(65))
> -- Всё просто и быстро!
> ```

```sql
LIMIT 10
```

### Создадим индекс, чтобы искать по ID

```sql
CREATE INDEX idx_perf_test_id ON perf_test(id);
```
Построение индекса может быть долгим.


Теперь после его создания попробуем повторить наш запрос. Запрос исполнится за ~50ms, вместо нескольких секунд. 
![[Pasted image 20251217004157.png]]

Однако мы можем делать такой поиск только по id, но не по reason и annotation, чтобы можно было сделать поиск и по ним, нужно создавать новые индексы.

> [!tip]- Пример
> ```sql
> SELECT *
> FROM perf_test
> WHERE reason LIKE 'bc%' AND annotation LIKE 'AB%' -- снова Seq Scan
> ```
> 

### Создаем индекс по другим столбцам

```sql
CREATE INDEX idx_perf_test_reason_annotation ON perf_test(reason, annotation);

EXPLAIN
SELECT *
FROM perf_test
WHERE reason LIKE 'bc%' AND annotation LIKE 'AB%';
```
После создания индекса по (reason, annotation) наш запрос исполняется моментально. 

> Однако построение индекса сразу по двум колонкам даёт нам возможность делать поиск лишь обоим колонкам сразу, либо по первой(reason). По annotation индекс нам никак не поможет с поиском, придется создавать новый индекс конкретно по annotation.

> [!tip]- Пример
> ```sql
> SELECT *
> FROM perf_test
> WHERE annotation LIKE 'AB%' -- поиск будет по Seq Scan, без индекса
> ```

Решение только одно, создавать индекс по annotation:
```sql
CREATE INDEX idx_test_annotation ON perf_test(annotation);
```

```sql
SELECT *
FROM perf_test
WHERE annotation LIKE 'AB%' -- теперь поиск по Bitmap Index Scan
```
![[Pasted image 20251217010545.png]]

> И снова есть нюанс. Если мы к примеру захотим привести поисковую строку в нижний регистр `LOWER(annotation) LIKE ('ab%')` то поиск снова будет последовательным. Для него снова нужно делать новый индекс, либо исключать подобные ситуации.


# .

Как мы писали ранее, в B-tree поддерживается 'bc%' но не поддерживается '%bc', значит этот индекс нам не подходит, если нам надо найти что-то в середине текста, а не в начале
> - Поддерживает `LIKE` 'abc%' (но не '%abc' )

С этим нам поможет индекс GIN

```sql
CREATE EXTENSION pg_trgm; -- запустить расширение

CREATE INDEX trgm_idx_perf_test_reason ON perf_test USING gin (reason gin_trgm_ops); -- ops = operations
```

Такой индекс создается довольно долго, но есть одна важная суть. Напишем запрос:

```sql
SELECT *
FROM perf_test
WHERE reason LIKE '%bc%' 
```
Казалось бы, мы создали индекс, а значит будет поиск по индексу. Но тут важный нюанс. Таких строк, в которых есть 'bc' в любой части, очень очень много, и последовательный поиск будет длиться возможно меньше времени, чем по индексу. В нашем случае это так и сработает, если ищем по '%bc%' то получаем Sequantial Scan
Но стоит нам сделать выборку поменьше, например '%bce%' так сразу метод сканирования меняется на Bitmap Scan.

> То есть нам не гарантируется поиск по индексам, если последовательный по времени выходит быстрее.
