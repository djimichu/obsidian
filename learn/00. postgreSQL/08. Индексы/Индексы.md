# **Индексы**.

- Индекс - объект БД, который можно создать и удалить
- Позволяет искать значения без полного перебора
- Оптимизация выборки "небольшого" числа записей
- "Небольшое" число - число относительное кол-ва записей в таблице
- По PRIMARY KEY и UNIQUE столбцам индекс создаётся автоматически (B-tree)
- Индексы не бесплатны

### Типы индексов.

Если мы введём:
```sql
SELECT amname FROM pg_am;
```

То мы получим типы индексов, доступные на нашем сервере. Обычно будет так:

- B-tree(сбалансированное дерево)
- Хеш-индекс
И специализированные индексы:
- GiST(обобщенное дерево поиска) (Generalized Search Tree)
- GIN (обобщённый обратный) (Generalized Inverted Index)
- SP-GiST(GiST с двоичным разбиением пространства)
- BRIN(блочно-диапазонный)

## Покрывающие, составные, частичные

> [!important]- Составной индекс
> Составной индекс - индекс **по нескольким колонкам сразу**
> Пример:
> 
> ```sql
> CREATE INDEX idx_users ON users (country, age);
> ```
> 
> Что это значит?
> 
> Индекс будет отсортирован:
> 
> 1. Сначала по `country`
>     
> 2. Внутри одной страны — по `age`
>     
> 
> Пример структуры (логически):
> 
> ```
> DE, 20  
> DE, 30  
> DE, 40  
> FR, 25  
> FR, 35  
> US, 18  
> US, 22
> ```
> 
> Плохо работает для поиска по второму полю:
> ```sql
> WHERE age = 30
> ```

> [!tip]- Покрывающий индекс
> Это ситуация, когда:
> 
> > Все нужные данные для запроса уже находятся в индексе.
> 
> Пример:
> 
> Таблица:
> 
> ```
> id | email | name
> ```
> 
> Создали индекс:
> 
> ```sql
> CREATE INDEX idx_email_name ON users (email, name);
> ```
> 
> Теперь запрос:
> 
> ```sql
> SELECT name FROM users WHERE email = 'a@b.com';
> ```
> 
> База:
> 
> 1. Идёт в индекс
>     
> 2. Находит email
>     
> 3. И там же видит name
>     
> 4. Не идёт в таблицу вообще
>     
> 
> Это называется:
> 
> > Index Only Scan
> 
> То есть не нужно второе чтение таблицы.

> [!tip]- Частичный индекс
> Это индекс не на всю таблицу, а **только на часть строк**.
> 
> Пример:
> 
> ```sql
> CREATE INDEX idx_active_users  
> ON users (email)  
> WHERE is_active = true;
> ```
> 
> Что это значит?
> 
> В индекс попадут только строки, где `is_active = true`.
> 
> ---
> 
> ## Зачем это нужно
> 
> Если:
> 
> - 90% пользователей неактивные
>     
> - 10% активные
>     
> - и ты часто ищешь только активных
>     
> 
> Тогда:
> 
> - индекс будет меньше
>     
> - поиск будет быстрее
>     
> - обновления дешевле

## Методы сканирования

Тут будут методы, которыми происходит сканирование данных:

- Индексное (index scan)
	- Если есть большой набор проиндексированных данных и мы осуществляем поиск по индексу и потенциально в результирующий набор попадает малое кол-во строк, то оптимизатор включит индексный поиск
	- Пример: ищем строку по конкретному целочисленному значению, некому айдишнику в проиндексированном столбце. На миллион записей нам попадет одна строка. Как раз index scan.
	>[!tip]- Пример
"Возьми картотеку (индекс), найди там "Война и мир" → увидишь номер полки 5-2 → иди к полке 5, книга 2"
>
**Когда:** Нужно найти ОДНУ книгу "Война и мир"  
**Аналог:** `SELECT * FROM books WHERE isbn = '978-5-...'` (уникальный ISBN)

- Исключительно индексное сканирование (index only scan)
	- Некоторые индексы(не все) хранят вместе с ID строк, сами проиндексированные значения. Это позволяет им просто читать сам индекс без обращения к таблицам и забирать результат прямо из самого индекса. Вместо чтения значения из таблиц при таком сканировании необходимо лишь заглянуть в VM(visibility map), чтобы выяснить актуальность индексных записей. Потому что как раз та самая карта видимости(VM) выставляет бит в единицу относительно определенной странице, показывает оптимизатору что можно выполнить исключительно индексное сканирование, что он не напорется на неактуальные данные, там лишь актуальные.
	- Для этого метода нужно запускать команду VACUUM, чтобы шло именно index only scan, а не менее эффективный index scan.
	>[!tip]- Пример
"Посмотри в картотеке (индексе) - там уже написано "Толстой, 1869 г." → не ходи к полке, всё в картотеке!"
>
**Когда:** Нужен только автор и год `SELECT author, year FROM books WHERE isbn = '...'`  
**Условие:** В картотеке (индексе) уже есть автор и год


- Сканирование по битовой карте (bitmap scan)
	- Если нам нужно вернуть не так много значений как при последовательном сканировании, но и не так мало как при index scan (например не 1 и не 9.990 из 10.000 значений), в таком случае планировщик может переключится на bitmap scan
	- Сначала метод доступа возвращает все TID(tuple ID), соответствующие условию и по ним строится битовая карта [^1]версии строк. Затем версии строк читаются из таблицы, притом каждая страница будет прочитана только один раз, уменьшая джампы между страницами
	>[!tip]- Пример
"Возьми картотеку, отметь закладками 10 книг Толстого → потом сходи и принеси ВСЕ эти книги за один подход"
>
**Когда:** Нужно найти 100 книг Толстого (не 1, но и не все 1000)



- Последовательное сканирование (sequential scan)
	- Чем меньше строк удовлетворяет запросу, тем эффективнее работает index scan и наоборот, при слабой селективности условия зачастую планировщик переключается в sequential scan из-за высоких накладных расходов при разнобойном чтении страниц индекса
	 >[!tip]- Пример
	>"Иди и проверь КАЖДУЮ книгу на полке"
>
**Когда** нужно найти ВСЕ книги автора "Толстой" (их много)  
**Аналог:** `SELECT * FROM books WHERE author = 'Толстой'` (если 40% книг)


Включение тех или иных методов сканирования находится в епархии оптимизатора.
Именно оптимизатор решает, включать ли какие-то методы поиска или исключать.

[^1]: версионирование строк. Postgres трэкает(отслеживает) версии строк. По ним и строится битовая карта

## Типы индексов. Подробно

#### Balanced Tree
- Создается по умолчанию 
	```sql 
	CREATE INDEX index_name ON table_name (column_name);
	```
- Поддерживает операции: <, >, <=, >=, = как и BETWEEN и IN
- Поддерживает `LIKE` 'abc%' (но не '%abc' )
- Индексирует `NULL`
- Сложность поиска O(logN) (логарифмическая сложность)

> [!NOTE]- Как работает
> Индекс хранит email **отсортированными**.
> 
> Например:
> 
> ```
> a@a.com  
> a@b.com  
> a@c.com  
> b@a.com  
> b@b.com  
> ...
> ```
> 
> Теперь поиск происходит как в словаре.
> 
> Ты не читаешь все 100 записей.
> 
> Ты:
> 
> 1. Смотришь “в середину”
>     
> 2. Понимаешь — идти левее или правее
>     
> 3. Спускаешься
>     
> 4. За 6–7 шагов находишь нужное
>     
> 
> Сложность:
> 
> > O(log N)

#### Hash
- 
	```sql
	CREATE INDEX index_name ON table_name USING HASH (column_name); 
	```
- Поддерживает только операцию "="
- Теперь отражается в журнале предзаписи (WAL)(Write-Ahead Log) - плюс
	- Журнал представляет собой стандартный метод обеспечения целостности данных
	- Изменения файлов с данными (таблицы, индексы и т.д.) должны записываться только после того, как эти изменения будут записаны в журнал
	- Можно восстановить базу данных с помощью этого журнала
	- Без него в случае сбоя пришлось бы восстанавливать индекс при помощи `REINDEX`, что очень долго
- Не рекомендуется к применению (в общем и целом)
- Сложность поиска O(1) - константное время


### Специализированные индексы
#### GiST

- Применяется для индексации геометрических типов данных и текстовых, для организации полнотекстового поиска.
- Занимает меньше места на диске чем GIN, однако может быть менее эффективен за счет дополнительных проверок

> [!tip]-  Примеры
> ```sql
> -- 1. География (координаты)
> WHERE точка_на_карте <-> моя_точка < 1000  -- в радиусе 1км
> 
> -- 2. Геометрия (фигуры)
> WHERE прямоугольник && другой_прямоугольник  -- пересекаются?
> 
> -- 3. Диапазоны дат/чисел  
> WHERE период @> дата  -- содержит ли период эту дату?
> 
> -- 4. Текстовый поиск (ранние версии)
> WHERE текст @@ 'кошка & собака'  -- содержит и кошка, и собака
> ```

> [!example]- Поиск кафе рядом
> ```sql
> -- Установи расширение
> CREATE EXTENSION postgis;
> 
> -- Таблица кафе с координатами
> CREATE TABLE cafes (
>     id SERIAL PRIMARY KEY,
>     name TEXT,
>     location GEOGRAPHY(Point)  -- широта/долгота
> );
> 
> -- GiST индекс для географического поиска
> CREATE INDEX idx_cafes_location ON cafes USING gist(location);
> 
> -- Найти кафе в радиусе 500 метров от меня
> SELECT * FROM cafes 
> WHERE ST_DWithin(
>     location, 
>     ST_Point(37.6173, 55.7558)::GEOGRAPHY,  -- Москва, Кремль
>     500  -- метров
> );
> ```

#### GIN

- Обычно применяется для массивов или набора значений. Массивы, ренж типы(диапазоны), JSONB(пары ключ-значение)
- Можно использовать для организации полнотекстового поиска, причем с более сложными запросами по тексту, чем мы описывали в B-Tree.

> [!tip]- Примеры
> ```sql
> -- 1. Массивы тегов
> WHERE теги @> ARRAY['любовь', 'драма']  -- содержит оба тега
> 
> -- 2. Полнотекстовый поиск
> WHERE описание @@ to_tsquery('кошка & собака')  -- и кошка, и собака
> 
> -- 3. JSON/JSONB
> WHERE json_data @> '{"age": 25, "city": "Moscow"}'
> 
> -- 4. Составные типы
> WHERE (name, age) = ('Иван', 25)
> ```

> [!example]- Поиск по тегам (как в Instagram)
> ```sql
> -- Таблица постов с тегами
> CREATE TABLE posts (
>     id SERIAL PRIMARY KEY,
>     title TEXT,
>     tags TEXT[]  -- массив тегов
> );
> 
> -- GIN индекс для массива
> CREATE INDEX idx_posts_tags ON posts USING gin(tags);
> 
> -- Найти посты с тегами "путешествия" И "горы"
> SELECT * FROM posts 
> WHERE tags @> ARRAY['путешествия', 'горы'];
> 
> -- Найти посты с ЛЮБЫМ из тегов
> SELECT * FROM posts 
> WHERE tags && ARRAY['путешествия', 'еда'];
> ```

#### SP-GiST

- Для набора данных с естественной упорядоченностью, но не являющихся сбалансированными.
- Например телефонные номера, первая половина номеров зависит от страны и города, а вторая +- случайна и не имеет выраженного баланса
- Для специалистов с отличными познаниями в математике. Новичок пользоваться не сможет.

#### BRIN

- Полезен на огромных наборах данных, которые подразумевают естественную упорядоченность, например почтовые индексы или TAIMSTAMP(временные метки), какие-то котировки и т.д
