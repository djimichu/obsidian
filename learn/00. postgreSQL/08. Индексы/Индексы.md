# **Индексы**.

- Индекс - объект БД, который можно создать и удалить
- Позволяет искать значения без полного перебора
- Оптимизация выборки "небольшого" числа записей
- "Небольшое" число - число относительное кол-ва записей в таблице
- По PRIMARY KEY и UNIQUE столбцам индекс создаётся автоматически (B-tree)
- Индексы не бесплатны

### Типы индексов.

Если мы введём:
```sql
SELECT amname FROM pg_am;
```

То мы получим типы индексов, доступные на нашем сервере. Обычно будет так:

- B-tree(сбалансированное дерево)
- Хеш-индекс
И специализированные индексы:
- GiST(обобщенное дерево поиска)
- GIN (обобщённый обратный)
- SP-GiST(GiST с двоичным разбиением пространства)
- BRIN(блочно-диапазонный)

### Методы сканирования

Тут будут методы, которыми происходит сканирование данных:

- Индексное (index scan)
	- Если есть большой набор проиндексированных данных и мы осуществляем поиск по индексу и потенциально в результирующий набор попадает малое кол-во строк, то оптимизатор включит индексный поиск
	- Пример: ищем строку по конкретному целочисленному значению, некому айдишнику в проиндексированном столбце. На миллион записей нам попадет одна строка. Как раз index scan.
	>[!tip]- Пример
"Возьми картотеку (индекс), найди там "Война и мир" → увидишь номер полки 5-2 → иди к полке 5, книга 2"
>
**Когда:** Нужно найти ОДНУ книгу "Война и мир"  
**Аналог:** `SELECT * FROM books WHERE isbn = '978-5-...'` (уникальный ISBN)

- Исключительно индексное сканирование (index only scan)
	- Некоторые индексы(не все) хранят вместе с ID строк, сами проиндексированные значения. Это позволяет им просто читать сам индекс без обращения к таблицам и забирать результат прямо из самого индекса. Вместо чтения значения из таблиц при таком сканировании необходимо лишь заглянуть в VM(visibility map), чтобы выяснить актуальность индексных записей. Потому что как раз та самая карта видимости(VM) выставляет бит в единицу относительно определенной странице, показывает оптимизатору что можно выполнить исключительно индексное сканирование, что он не напорется на неактуальные данные, там лишь актуальные.
	- Для этого метода нужно запускать команду VACUUM, чтобы шло именно index only scan, а не менее эффективный index scan.
	>[!tip]- Пример
"Посмотри в картотеке (индексе) - там уже написано "Толстой, 1869 г." → не ходи к полке, всё в картотеке!"
>
**Когда:** Нужен только автор и год `SELECT author, year FROM books WHERE isbn = '...'`  
**Условие:** В картотеке (индексе) уже есть автор и год


- Сканирование по битовой карте (bitmap scan)
	- Если нам нужно вернуть не так много значений как при последовательном сканировании, но и не так мало как при index scan (например не 1 и не 9.990 из 10.000 значений), в таком случае планировщик может переключится на bitmap scan
	- Сначала метод доступа возвращает все TID(tuple ID), соответствующие условию и по ним строится битовая карта [^1]версии строк. Затем версии строк читаются из таблицы, притом каждая страница будет прочитана только один раз, уменьшая джампы между страницами
	>[!tip]- Пример
"Возьми картотеку, отметь закладками 10 книг Толстого → потом сходи и принеси ВСЕ эти книги за один подход"
>
**Когда:** Нужно найти 100 книг Толстого (не 1, но и не все 1000)



- Последовательное сканирование (sequential scan)
	- Чем меньше строк удовлетворяет запросу, тем эффективнее работает index scan и наоборот, при слабой селективности условия зачастую планировщик переключается в sequential scan из-за высоких накладных расходов при разнобойном чтении страниц индекса
	 >[!tip]- Пример
	>"Иди и проверь КАЖДУЮ книгу на полке"
>
**Когда** нужно найти ВСЕ книги автора "Толстой" (их много)  
**Аналог:** `SELECT * FROM books WHERE author = 'Толстой'` (если 40% книг)


Включение тех или иных методов сканирования находится в епархии оптимизатора.
Именно оптимизатор решает, включать ли какие-то методы поиска или исключать.

[^1]: версионирование строк. Postgres трэкает(отслеживает) версии строк. По ним и строится битовая карта
