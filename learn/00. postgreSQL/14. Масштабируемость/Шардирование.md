# Шардирование.

**Простыми словами:** Это то же партиционирование, но **куски (шарды) раскидываются по разным физическим серверам (нодам)**. Каждый шард — это практически независимая маленькая база данных.

**На примере:**  
У нас глобальное приложение с пользователями из разных стран.

- **Шард 1 (сервер в Германии):** пользователи из Европы (id пользователя с 1 по 10млн)
    
- **Шард 2 (сервер в США):** пользователи из Америки (id с 10млн+1 по 20млн)
    
- **Шард 3 (сервер в Сингапуре):** пользователи из Азии (id с 20млн+1 и дальше)
    

**Зачем?**

- **Масштабирование записи:** Запись теперь распределяется по серверам! Это главный плюс.
    
- **Огромный объём данных:** Данные просто не влезут на один диск.
    
- **Геоблизость:** Европейские пользователи ходят на сервер в Германии — быстрее ответ.
    

**Минусы (СЛОЖНОСТИ!):**

- **Сложные запросы:** `SELECT * FROM all_users` нужно делать по всем шардам и потом результаты склеивать.
    
- **Джойны между шардами:** Крайне неэффективны, почти невозможны.
    
- **Роутинг:** Приложение должно понимать, в какой шард идти за данными.
    
- **Ребалансировка:** Если один шард перегружен, данные нужно перераспределять — сложная операция.
    

**Как объяснить на собесе:** "Это горизонтальное масштабирование БД путём разделения данных на независимые части (шарды) и распределения их по разным серверам. Решает проблемы с объемом данных и нагрузкой на запись, но сильно усложняет архитектуру и выполнение сложных запросов."

Также есть вертикальный шардинг, но используется он реже, по колонкам (фотографии пользователя и тд.)
