# Партиционирование.

Это когда **одна таблица внутри одной базы** делится на части.

- работает внутри одного сервера
    
- одна база
    
- один WAL
    
- одна точка отказа
    

Это не масштабирование “по серверам”.

Логически для тебя это одна таблица:

```sql
SELECT * FROM orders;
```

Но физически она разбита на куски:

- orders_2023
    
- orders_2024
    
- orders_2025

> [!tip]- Зачем это нужно
> Если таблица очень большая (миллионы/миллиарды строк):
> 
> - запросы начинают тормозить
>     
> - индексы разрастаются
>     
> - VACUUM становится тяжёлым
>     
> 
> Если разделить по годам:
> 
> - запрос за 2025 будет читать только одну партицию
>     
> - остальные даже не тронет
>     
> 
> Это называется **partition pruning** — база автоматически выбирает нужный кусок.

### Виды партиций.

> [!tip]-  Range (по диапазону)
> ```
> 2023 → в одну партицию  
> 2024 → в другую
> ```
> 
> Обычно по дате.

> [!tip]- List (по списку значений)
> Например:
> 
> ```
> country = 'DE'  
> country = 'US'  
> country = 'FR'
> ```

> [!tip]- Hash (по хешу)
> Данные распределяются равномерно по N частям.

# Шардирование

Шардирование — это когда:

> данные делятся между разными серверами

Пример:

- сервер 1 — пользователи с id 1–1 000 000
    
- сервер 2 — пользователи 1 000 001–2 000 000
    

Это уже распределённая система.

---

## Зачем шардирование

Когда:

- один сервер больше не справляется
    
- нужно горизонтальное масштабирование

> [!warning]- Сложности
> Теперь появляются проблемы:
> 
> - как найти нужный сервер?
>     
> - что делать с JOIN между шардами?
>     
> - как делать транзакции между серверами?
>     
> - как перераспределять данные?
>     
> 
> Это уже архитектурная сложность.



# Разница коротко

|Партиционирование|Шардирование|
|---|---|
|Один сервер|Несколько серверов|
|Одна БД|Несколько БД|
|Прозрачно для приложения|Приложение обычно знает о шардах|
|Для удобства и производительности|Для масштабирования|
